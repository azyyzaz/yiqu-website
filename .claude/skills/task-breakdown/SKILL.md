# task-breakdown —— 拆到能打分的粒度

本组两个已确认的痛点都由这个 skill 兜：

- **收尾漂移** —— 联调、上线、维护那些任务从来没被列出来过、也没被算过工时，所以只能"顺便做掉"，所以必然超标
- **任务拆不开** —— 任务卡上写的是「提升代码质量」这种话，于是没人知道什么时候算完

## 铁律：可打分的任务必须同时满足四条

> **动词开头 · 一个人做 · 一段连续时间 · 做完能交出一样东西**

任何一条不满足，就不是任务，是口号。**遇到口号要打回重写，不要硬拆。**

| 打回 | 改成 |
|---|---|
| 提升代码质量 | 每次提交前跑一遍 lint 和单测，失败项记到 issue |
| 做好测试 | 每周手工执行一遍主流程回归用例，记录失败项 |
| 完善文档 | 每个接口写完当天补 200 字说明给对接方 |
| 优化性能 | 把首页首屏从 3.2s 压到 1.5s 以内 |
| 加强沟通 | 每天 15 分钟站会，说清昨天做了什么 / 今天做什么 / 卡在哪 |

## 工作流

1. **读需求** —— 原始需求、聊天记录、口头反馈都行
2. **定位价值链段** —— 每一条任务必须归到下面 7 段之一
3. **拆** —— 一次拆 8~10 条。少于 5 条通常意味着拆得还不够细
4. **写数字** —— **频次和耗时必须写数字**，不许写「经常」「比较多」
5. **算总账** —— 跑 `scripts/sum_hours.py` 得到分段的每周人时合计
6. **标 owner** —— 每条写清谁做，**必须是单个的人**，不能写「大家一起」

## 价值链段

```
接需求 · 评估排期 · 设计 · 编码 · 联调测试 · 上线交付 · 维护响应
```

拆到「联调测试」还不够，要再往下一层：

> 「联调测试」拆开：写接口文档给对接方 · 跑主流程回归 · 复现失败项 · 回归验证修复
>
> 「上线交付」拆开：写发版说明 · 准备上线检查清单 · 定回滚方案 · 部署 · 通知需求方 · 收验收确认

**停在「测试」这两个字上，没有频次也没有耗时。** 这句话是判断拆够没够的唯一标准。

## 输出格式

固定用这张表，不要自由发挥：

```markdown
| # | 任务 | 价值链段 | 谁做 | 频次 | 每周耗时 |
|---|---|---|---|---|---|
| ① | 每次发版手工执行一遍主流程回归 | 联调测试 | 组员B | 每周 | 6 人时 |
```

表下面附一段：

```
收尾相关（联调测试 + 上线交付 + 维护响应）合计：__ 人时/周
→ 这就是收尾的真实工期，拿去反向排期
```

## 算完总账之后必须说的一句话

把收尾那几段的人时加起来，**明确告诉用户这个数字**，并接一句：

> 这个数字以前不在你的排期里，所以它每次都变成"意外"。

## 排期动作（拆完之后）

反向排期，每个节点都有工期：

```
交付日
 └— 封版日（停止接任何变更）
     └— 验收演示日
         └— 联调测试完成日
             └— 功能开发完成日
```

**收尾要占整个周期的 30%~40%。** 这个比例是 0 的排期，漂移是必然的。

## 脚本

```bash
python3 .claude/skills/task-breakdown/scripts/sum_hours.py tasks.json
```

`tasks.json` 格式见脚本头部注释。stdlib，无依赖。
