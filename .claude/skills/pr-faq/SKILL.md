# pr-faq —— 先写终点，再决定要不要出发

方法来自亚马逊的逆向工作法：**新闻稿和 FAQ 先写，产品后做**，
写法是「假装已经上线了」，用完成时态描述结果。

本组痛点①「想法从原型到落地」，病根不是做得慢，而是**终点一开始就没写清楚**。
做到哪算完只能靠感觉，而感觉每次都不同 —— 这就是收尾漂移的源头。

## 铁律：通篇不许出现未来时态

> **将 · 计划 · 未来 · 打算 · 后续 · 预计 · 将要 · 即将 · 届时 · 争取 · 目标是**

写成「已经上线」的口吻。**写不出来，说明这件事的终点还没想清楚，
那它就还没到能排期的时候。**

这是 G1 唯一一条不能商量的规则。它可机检，所以它进了检查项，不靠自觉。

## 什么时候要写

| 要写 | 不用写 |
|---|---|
| 占工时 ≥ 2 天 | 改错别字 |
| 用户能直接感知的改动 | 内部重构、行为不变 |
| 需求方提出来、要跨人协作 | 昨天说今天做的小修补 |

门槛定太低，第一次改个错别字也要写新闻稿，这套东西活不过一周；
定太高，又回到「收尾那天才想清楚终点」的老路。

## 一页纸的模板

```markdown
# <项目名>

## 新闻稿

<公司名>今天宣布 <一句话说清做了什么>。

在此之前，<谁> 遇到 <什么具体问题>，只能 <现在用什么笨办法>，
<代价是什么，写到数字>。

现在，<谁> 在 <哪里> <做几步>，直接得到 <结果>。
<同样的活，从多久变成多久>。

「<用户原话，一句就够>」
　　　　　　　　　　　　　　—— <谁说的，具名到岗位>

## 常见问题

1. 为什么现在做？
2. 谁用？用它的频率是？
3. 怎么用？从哪进、几步完成？
4. 跟已有功能是什么关系？替换还是新增？
5. 数据从哪来，权限怎么控？
```

五个问题的详细判断标准见 `references/faq-five.md`。

**第 5 问是 to B 业务的签单关键**，别省。企业客户最先问的就是数据从哪来、谁能看。

## 工作流

1. **问清终点** —— 这件事做完之后，谁的生活发生了什么变化
2. **按模板写** —— 五个 FAQ 全部要有答案，**不许留「待定」「再议」**
3. **自检** —— 跑脚本
4. **交 G1** —— 组长核（提案人就是组长时，交任一未参与的组员核）

引言的规矩：**写不出来就写「这句话还没问到」**，不要编一句凑上。
编的引言会在路演或验收现场被问穿。脚本会把编造痕迹（占位符）标出来。

## 脚本

```bash
python3 .claude/skills/pr-faq/scripts/check_prfaq.py docs/pr-faq/<项目名>.md
```

查四件事：未来时态词 / 待定词 / 五问齐不齐 / 有没有引言。
退出码 0 = 可以过 G1。stdlib，无依赖。

**注意**：脚本会跳过 ``` 围起来的代码块，所以规则说明可以放心抄进文件——
但更省事的做法是把规则写在文件外面。

## 关卡位置

```
接需求 ──▶ ◆G1 需求冻结 ──▶ 评估排期
              │
              └ 通过条件：docs/pr-faq/<项目名>.md 存在、非空、脚本退出码为 0
                 不过：不进排期，退回提案人（具体到人，不打回给「相关部门」）
```
