# release-check —— 把收尾变成流程

「每次收尾都漂移很多」的根因：**收尾的动作从来没被列出来过，也就从来没被算过工时。**
它不在排期里，所以只能是"顺便做掉"，所以必然超标。

这个 skill 把手册第 3 章那些收尾任务固化成一张每次都要走的单子。
**走完它，收尾就从一个"意外"变成一个"已知工期"。**

## 发版前必做的三件事（顺序不能反）

1. **确认封版** —— 本次要发的东西全部冻结，**新需求默认进下一版**
2. **过检查清单** —— `references/checklist.md` 逐条走，不许跳
3. **写回滚方案** —— `references/checklist.md` 最后一节。**没有回滚方案不许发版**

## 封版日的规则（组长的活，不能下放）

过了封版日：

- 新需求**默认进下一版**，只接 P0 级 bug
- 谁要改，让他**二选一**：确认「延期 X 天」，或者「砍掉 Y 功能」
- **没见到确认就不接**

这条最难执行，尤其是需求方是老板或客户的时候。但它是唯一能真正止住范围漂移的东西。

## 输出物（每次发版固定四样）

| 产出 | 内容 | 谁 |
|---|---|---|
| 发版说明 | 改了什么、影响谁、要不要用户做什么 | 用 `scripts/gen_notes.py` 起稿，人工改 |
| 上线检查清单 | 逐条勾，勾不动的写明原因 | 发版人 |
| 回滚方案 | 触发条件 + 步骤 + 谁拍板 | 组长 |
| 验收确认 | 需求方那一句「确认收到」 | 组长去要 |

**第四样最容易漏。** 没有验收确认，这个版本就不算交付完成 —— 下个项目开始时它还会被翻出来。

## 生成发版说明

```bash
python3 .claude/skills/release-check/scripts/gen_notes.py v1.2.0 HEAD
```

按类型分组，自动跳过 merge commit 和纯格式提交。**脚本只起稿，发出去之前必须人工过一遍** —— 它不知道哪些改动对用户重要。

## 上线之后

- **观察 30 分钟** —— 看错误日志和关键路径，别发完就走
- **当天写复盘** —— 如果出了 P0，当天写，不要拖到第二周
- **把本次收尾的真实耗时记下来** —— 这是 `task-breakdown` 里 D 维度（数据）的原料。没有历史工时，「开发周期较长」这条的 D 永远是 2

## 和排期的关系

走完一次，你会得到一个真实的收尾工时数字。**把它填回排期**：

```
交付日
 └— 封版日
     └— 验收演示日
         └— 联调测试完成日
             └— 功能开发完成日
```

收尾应占整个周期的 **30%~40%**。这个比例是 0 的排期，漂移是必然的。
