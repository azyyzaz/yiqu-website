# api-contract —— 先把接口写死，再动手

收尾对不上的头号原因，是**两边各自以为接口长什么样**。
到了联调那天才发现：一边返回 `null`，一边等着空数组；一边当 500 处理，一边发的是 400。

契约就是把这个"以为"提前变成文件。

## 铁律：五要素缺一不可

> **路径 · 字段与类型 · 错误码 · 边界情况 · 示例**

少任何一条，这份契约就挡不住联调那天的争吵。

**其中最常漏的是「边界情况」。** 它也是唯一一条不写就一定会在联调时爆的 ——
因为正常路径两边都会测，异常路径两边都假设对方会处理。

边界情况有一份现成的过审清单，见 `references/boundaries.md`。**写之前先过一遍那十条。**

## 模板

```markdown
# <项目名> · 接口契约

冻结于 <日期>

## <METHOD> <路径>

请求参数
  <字段>   <类型>   <必填/可选>   <说明，含取值范围>

响应
  <状态码>  <类型与结构>
           <关键的响应头>

错误
  <状态码>  <触发条件>           <响应体>

边界
  · <异常路径一：怎么触发，返回什么>
  · <异常路径二>

示例
  <一段真实的请求与响应，不是占位符>

## 签字

  提出方 ____________  日期 ________
  对接方 ____________  日期 ________
```

一个项目多个接口就重复「## 接口」这一段。**每个接口都要单独过五要素**，
不能第一个写全了后面几个就省。

## 冻结的含义

过了 G2 这道门，**改契约要走变更单，不能直接改文件**。

变更单不必是张表，在文件末尾追加一段就够：

```markdown
## 变更

2026-09-24  对接方：导出的 filename 改成带日期，前端不用改   （组长确认）
```

留痕的意义不在追责，在于**联调出问题时能一眼看出"这是什么时候变的"**。
没有变更记录，两个人会在"明明说好了"上吵一下午。

## 工作流

1. **谁写** —— 本次主程。他离实现最近，也最清楚哪些地方含糊
2. **过边界清单** —— `references/boundaries.md` 十条逐条过，不适用的明确写「不适用，因为…」
3. **自检** —— 跑脚本，五要素和签字都会被查
4. **双方各签一次** —— 提出方 + 对接方
   - 单人全栈项目凑不出「双方」时，由未参与的一人代签，**签字栏注明「代签」**
5. **交 G2** —— 两人都签完才算过

**不接受「边做边定」。** 那是收尾对不上的头号原因，也是这道关卡存在的全部理由。

## 脚本

```bash
python3 .claude/skills/api-contract/scripts/check_contract.py docs/contract/<项目名>.md
```

查四件事：每个接口的五要素齐不齐 / 边界清单覆盖了几条 / 签字栏有没有名字和日期 / 有没有变更记录格式。
**边界覆盖率是「提示」不是「判定」** —— 它只负责提醒你别漏，覆盖不到不等于错。
stdlib，无依赖。

## 关卡位置

```
设计 ──▶ ◆G2 方案定稿 ──▶ 编码
            │
            └ 通过条件：docs/contract/<项目名>.md 存在，双方各签过一次
               不过：不许开工。「边做边定」不接受
```

## 与 pr-faq 的接续

`pr-faq` 写的是**要什么**（用户视角），这份写的是**怎么给**（接口视角）。
PR/FAQ 里问不出「空结果返回什么」，那份文件不该写这个 —— 那是契约的活。

**前者说不清的，后者要能补上；后者补不上的，说明前者还没想清楚。**
